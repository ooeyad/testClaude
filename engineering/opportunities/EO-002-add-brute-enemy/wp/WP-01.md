# WP-01 — Brute definition and load order

**Status:** todo · **Depends:** — · **Refs:** AD-001, AD-003, AD-005, INV-2, INV-4, STD-20, STD-21, STD-26

## Contract

**Goal.** Register a new enemy type `brute` as pure data, loaded in the right
place, so that it exists in the registry and spawns correctly — while no wave
references it yet and the game plays exactly as before.

**Done when.**
1. `phefo/js/entities/enemies/brute.js` exists and follows the same shape as its
   four peers: `window.Phefo = window.Phefo || {}; (function (P) { 'use strict'; … })(window.Phefo);`
   containing exactly one `P.Enemies.define({...})` call and nothing else.
2. `phefo/index.html` has one new `<script src="js/entities/enemies/brute.js"></script>`
   line immediately after the `archer.js` line. No other line changes.
3. After boot, `Phefo.Enemies.registry.brute` is an object, and
   `Phefo.Enemies.spawn('brute', 500, 0)` returns an instance with
   `hp === 150` and `knockScale === 0.28`.
4. `node --check` passes for every script listed in `index.html`, in order.
5. The game boots with no thrown error and no new console error.
6. `git diff --stat` lists exactly two paths.

**Touches.**
- `phefo/js/entities/enemies/brute.js` — **new**
- `phefo/index.html` — **one added line only**

**Forbidden.**
- `phefo/js/entities/enemy.js` — the shared state machine. Everything this
  package needs already exists there as a config key. Opening it to edit is a
  gate failure (condition C-1).
- `phefo/js/entities/enemies/{knifeman,swordsman,gunman,archer}.js` — condition C-1.
- `phefo/js/combat/weapons.js` and `phefo/js/render/stickman.js` — no new weapon
  (condition C-2).
- `phefo/js/levels/level01_city.js` — that is WP-02. Do not place the brute yet.

**Must not change.** The behaviour of the four existing enemy types. This holds
structurally: their files are not opened, `enemy.js` is not opened, and a new
registry key is unreachable by any existing wave entry.

## Notes
- **The exact config keys `Enemy` reads** — anything else is silently ignored, so
  do not invent one: `type weapon hp speed aggro scale knockScale blocks
  telegraph attackDur recover hitAt shotTimes color warnColor attack`
  (plus `ranged preferred minRange` for ranged types, which this is not).
- **Values, decided and fixed:** `type:'brute'`, `weapon:'sword'`, `hp:150`,
  `speed:78`, `aggro:380`, `scale:1.24`, `knockScale:0.28`, `telegraph:0.58`,
  `attackDur:0.50`, `recover:0.70`, `hitAt:0.20`. Do **not** set `blocks` —
  guarding is the swordsman's identity, and its absence is the design.
  Do **not** set `shotTimes` — a second hit would eat the recovery window that
  the whole fairness argument rests on.
- **Colours:** pick a heavier, cooler body colour than the swordsman's `#9aa4ad`
  and a hotter `warnColor` than its `#e8934a`, so the wind-up reads at a glance
  on the largest silhouette in the game.
- **The `attack` function** mirrors the swordsman's exactly in structure —
  `e.weapon()`, `P.Combat.origin(e)`, `P.Combat.centre(world.player)`,
  `Math.atan2`, `P.Audio.play(w.sound || 'slash')`,
  `P.Combat.meleeSweep(e, [world.player], w, angle, world)`, camera shake on a
  hit, then a committed step `e.vx += e.facing * N`. Never touch `hp` directly
  (STD-25). Use a heavier shake and a heavier step than the swordsman's 6 / 95.
- **Load order is load-bearing (INV-4).** `P.Enemies` is created by
  `entities/enemy.js` and read at IIFE-execution time, so the tag must come after
  it; `levels/*.js` name enemy types, so it must come before them. Immediately
  after `archer.js` satisfies both. `js/core/game.js` stays last in the file.
- **ES5 only (STD-21):** `var`, no arrow functions, no `let`/`const`, no template
  literals, no default parameters. Match the peers' comment style: a short block
  comment saying what role the type plays and why, not what the code does.
